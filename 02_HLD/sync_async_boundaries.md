# SALESTORM ARFA - Synchronous vs Asynchronous Architectural Boundaries

## 1. Architectural Philosophy: The Decoupled Flash Pipeline
The fundamental design flaw of traditional e-commerce architectures during flash sales is attempting to execute the entire transaction chain—Inventory Lock, User Validation, Payment Authorization, Order Record Creation, and Notification—within a single synchronous request-response HTTP cycle.

Under 10,000 requests per second, this causes:
1. **Thread starvation** on the web server connection pools.
2. **Cascading lock contention** on relational database row locks (`SELECT FOR UPDATE`).
3. **Connection pool exhaustion** while waiting for third-party payment gateways (Stripe latency P99 ~ 2,500ms).

SALESTORM enforces a strict architectural boundary dividing the system into two distinct operational planes:

```
[ INGRESS TRAFFIC (10,000 RPS) ]
               │
               ▼
┌───────────────────────────────────────────────┐
│     SYNCHRONOUS RESERVATION PLANE             │
│  - In-Memory Redis Lua Engine                 │
│  - Execution latency: < 5ms                   │
│  - Client Latency P99: < 50ms                 │
│  - Emits: Signed Ephemeral Lease (300s TTL)   │
└───────────────────────────────────────────────┘
               │
               │ Async Event Handoff (Kafka Buffer)
               ▼
┌───────────────────────────────────────────────┐
│     ASYNCHRONOUS SETTLEMENT PLANE             │
│  - Transactional Outbox Pattern               │
│  - PostgreSQL ACID Order Ledger               │
│  - Stripe Payment Intent Authorization        │
│  - Rate-limited, smooth database consumption  │
└───────────────────────────────────────────────┘
```

## 2. Boundary Comparison Matrix

| Property | Synchronous Reservation Plane | Asynchronous Settlement Plane |
| :--- | :--- | :--- |
| **Primary Data Store** | Redis Cluster (In-Memory RAM) | PostgreSQL 16 (Durable NVMe SSD) |
| **Concurrency Primitive** | Single-threaded Lua script atomicity | ACID multi-version concurrency control (MVCC) |
| **Client Interaction** | Immediate HTTP 200 / 409 response | Polling / WebSockets / Push Notifications |
| **Latency SLO** | P99 < 50ms | P99 < 3,000ms |
| **Throughput Capacity** | 50,000+ operations/sec | 1,500 - 3,000 writes/sec |
| **Failure Blast Radius** | Isolated to inventory availability | Isolated to individual order fulfillment |
| **Durability Model** | In-memory with append-only file (AOF) | Synchronous WAL disk commit |

## 3. The Asynchronous Event Hand-Off Contract
When a reservation succeeds:
1. The inventory microservice emits an `InventoryReserved` event to Kafka topic `salestorm.inventory.reservations.v1`.
2. The user receives a cryptographically signed lease token containing:
   - `reservation_id` (UUIDv4)
   - `user_id`
   - `sku_id`
   - `expires_at` (Epoch timestamp, $+300s$)
   - `hmac_sha256` signature generated by the platform secret key.
3. The client transitions to the checkout interface. The downstream PostgreSQL database never sees the 9,900 failed requests; it only processes the 100 successful checkouts at a leisurely, controlled pace.
